### R-1 — self-granted privileges (critical)

`users_update_own` (`002_v1_rls_policies.sql:18`) scoped which *row* a caller may update but never which *columns*, and Supabase's default table-wide `GRANT UPDATE` made every column writable by its owner. The three privilege flags live on that same self-writable row (`043:20`, `046:35`, `110:20`).

Reachable consequences: publish arbitrary unreviewed AI health content to every user via `approve_content_row` (042:299); control the public events feed; free villie Pro.

**This also explains why migration 110's Pro gate looked airtight but wasn't.** The SQL enforcement in 110 is correct — playback ids nulled, RLS hides locked rows. The *flag it reads* was self-writable, so the gate was bypassed one level up. R-1 is what makes 110 actually hold.

Follows the `095` pattern, including its hard-won lesson: a column-level `REVOKE` is a **no-op** while a table-wide grant exists.

Verified by execution against Postgres 16 (stub schema, real grants): escalation `UPDATE` → `permission denied`; email takeover → `permission denied`; ordinary profile edit → succeeds; SELECT unaffected, so clients still read `is_pro`.

### R-2 — SMS and push open relays (critical)

Both functions carried an "Auth: service role only" header comment and performed **no authorization at all**. `verify_jwt = true` is not a substitute: it proves only that the bearer is signed by this project's JWT secret, and **the anon publishable key is exactly such a token** — it ships in the mobile bundle and on the marketing site.

This is the load-bearing insight of the whole review: it means every "server-only" function without an in-code gate is effectively internet-public *regardless of gateway settings*. Reachable: arbitrary SMS from Villie's Twilio number (toll fraud + smishing from a trusted number); arbitrary push to any user list, with caller-supplied `bypass_prefs: true` overriding notification preferences **and** quiet hours.

All 9 existing callers were verified to send `SUPABASE_SERVICE_ROLE_KEY` before gating, so no caller breaks.

### R-3 — specialist approval no-op (high)

`013_v1_admin_approval.sql:49` dropped `"Specialists are publicly readable"`; the policy actually created in `002:22` was named `specialists_select_all`. `IF EXISTS` swallowed the miss and the permissive `USING (true)` survived ~120 migrations. `015_v1_rls_audit.sql:3` asserts the control was in place, which is why it went unnoticed.

Exposed to **anon**: `phone`, `address_line1`, `stripe_account_id`, and `admin_rejection_reason` for pending and rejected practitioners.

Verified before dropping: the website never reads the table; 7 of 8 edge functions use service-role; the 8th (`create-payment-intent`) runs under the caller's JWT and retains `authenticated` read of approved rows.

### R-5 — fabricated clinical attribution (high)

`ManualScrollV3.tsx` substituted a placeholder titled "What to expect this week", attributed to **"Dr. Priya Nair, MD · pediatrician · villie"** — a person who does not exist — playing a public Mux sample clip.

Not an edge case: `get_manual_week_intro` filters `locale` exactly with no `en` fallback (`110:184-187`), so for a Spanish-speaking user under the English-first Pro launch **no week ever resolves** — she got the fake pediatrician on all 52 weeks, as did paying Pro subscribers in place of purchased content. `docs/PRO_VIDEO_LAUNCH_RUNBOOK.md`, added in the same commit as the locale-scope migration, documents the intended behaviour as "she gets no week-intro slot at all (it hides…)". Code contradicted its own runbook.

The `.catch` now also fails closed: it previously substituted a playable object carrying no `is_locked`, so `openWeekIntro` skipped the paywall — a transient network error handed free-tier users a playable card.

## Closed: `095` deferred item — donor `lat`/`lng` (no action)

`095_security_milk_donor_pii_column_revoke.sql:37-40` deferred revoking `milk_donor_profiles.lat/lng` pending verification. **Closing it: no change needed.**

- Coordinates are **ZIP-centroid derived**, not house-level geocodes (confirmed by the product owner, 2026-09-04). A ZIP centroid is coarser than the `zip_code` and `city` columns already selectable on the same row, so revoking buys no privacy.
- Independently, nothing in the repo writes these columns — no mobile code, no SQL, no edge function, no seed. They are populated out-of-band.
- A blanket revoke would be actively harmful: column grants are role-wide, not row-aware, so it would break a donor reading **her own** profile (`getMyDonorProfile`) and `listSavedDonors`. `DonorMapScreen` is unaffected either way — it reads through the `search_donors_near` SECURITY DEFINER RPC, which ignores column grants.

**Revisit only if** donor coordinates ever become precise geocodes. At that point the fix is a separate coarsened column plus jitter in `search_donors_near` — not a grant change.

## Remediation log, batch 4 (2026-09-05) — `events-harvest` SSRF

`body.probe.url` was fetched server-side from inside Supabase's network, on a function with **no authorization at all**. Two fixes, because the gate alone is not sufficient:

**1. Service-role gate.** Both legitimate callers are service role — the daily GH Actions cron (`supabase-crons.yml:57`, `BODY='{}'`) and ops running a probe by hand per `docs/OPS_RUNBOOK.md:75`. No mobile code calls it. This alone removes the internet-facing SSRF *and* stops anyone triggering the full Haiku harvest fan-out over every registered feed.

**2. URL guard with per-hop revalidation.** Still needed after the gate, because `fetchDirect` used `redirect: 'follow'` — so a *registered feed* URL that later redirects somewhere internal is the same hazard, and no gate covers it. Validating only the first hop is the classic way an SSRF check gets bypassed. `fetchDirect` now follows redirects manually (bounded at 5), revalidating **every hop**; `fetchRendered` validates before interpolating into the `r.jina.ai/` proxy path. Blocked: non-http(s) schemes, loopback, RFC1918, CGNAT, link-local (`169.254.*` — cloud metadata), IPv6 loopback/unique-local/link-local. The probe branch validates up front and returns a 400 naming the reason, because both fetch paths swallow errors into "no events extracted" — which is exactly the signal ops uses to decide *not* to register a feed.

**Verified by execution**, against the shipped code extracted from the file (not a reimplementation):
- Guard unit test: 15 hostile URLs blocked, 5 legitimate ones allowed — including boundary cases `172.32.0.1` and `100.128.0.1`, which sit just outside RFC1918/CGNAT and must *not* be blocked.
- Live redirect test under Deno: a normal redirect chain still resolves to page content (feeds don't break); a "public" URL redirecting to `169.254.169.254` throws `url_host_blocked` at the hop; a redirect loop terminates with `too_many_redirects`.
- Confirmed first that Deno's `redirect: 'manual'` exposes the real status and `Location` rather than an opaque response — if it did not, hop-following would have silently broken every redirecting feed, and per the runbook a zero-yield feed auto-deactivates after 3 days.

**Known limitation, stated rather than papered over:** this is a hostname/IP-literal check, not a resolved-address check. A hostname that *resolves* to a private address still passes, and DNS rebinding between check and fetch is not defeated. Closing that needs resolve-then-connect-by-IP with a pinned Host header, which is more machinery than this ops tool warrants now that it is service-role gated. The gate is the primary control; the guard is defence in depth.

This class existed because the codebase repeatedly recorded `verify_jwt` as authentication. Three examples, now corrected in place:

- `gear-cpsc-recall-sync`: *"the gateway rejects anything else with 401 before reaching here. No need for a redundant function-level check."* It does not — the anon key is a valid project JWT. The same comment records that the previous check was **deleted** because it "introduced an env-mismatch failure mode that broke this cron after the last key rotation" — which is the exact scenario `_shared/service-role.ts`'s two-mode gate was written for. Deleting authentication was never the fix. - `agents-*`: *"Callers must be authenticated (Supabase verifies JWT by default)."*
- `room-alias-generate`: *"Auth: authenticated user JWT (verify_jwt: true default)."*
- `docs/OPS_RUNBOOK.md:329` asserts `trending-compliance-pass -> 401 (JWT-locked, GOOD)`. That smoke test only passes because it sends **no** bearer; an anon-key holder sailed straight through. A green check that proves the wrong thing.

### Two that were worse than "no gate"

- **`milk-questionnaire-coach`** had a *presence* check: any non-empty `Authorization` header passed. It authenticated nobody — it merely re-confirmed the gateway had let the request in.
- **`room-alias-generate`** base64-decoded the JWT and trusted `sub` **without verifying the signature** — the same defect `_shared/service-role.ts` was created to kill after the 2026-08-14 incident, applied to a user id instead of a role. `Bearer x.eyJzdWIiOiI8YW55LXV1aWQ+In0.x` impersonated any user, and the alias is persisted against that id, so a caller could seed or overwrite another member's anonymous identity in a room. The user gates stop **anonymous** abuse: the endpoints are no longer reachable with the bundled anon key. They do **not** stop a signed-in user looping a request in a script. Every user-gated function above remains an unmetered per-account model endpoint billed to Villie.

Doing it properly needs a shared counter (a `usage_ledger` keyed on `(user_id, function, window)`, checked in `_shared/`), which is a migration plus a new failure mode on every call site — deliberately not bundled into a security pass. `room-ai-companion` already has a per-user/room/hour limit via `ai_companion_mentions` and is the working model to generalise.

## Remediation log, batch 6 (2026-09-06) — `pro-entitlement-reconcile`, the last unverified decode

The function decoded the bearer's payload and returned `role === 'service_role'` **without verifying the signature**, justified in-code by *"The gateway verifies the JWT signature; we only need to know WHICH role signed in."* That premise was false here specifically: this was the **only** function absent from the `verify_jwt` registry, so nothing established the gateway was checking signatures at all. `Bearer x.eyJyb2xlIjoic2VydmljZV9yb2xlIn0.x` drove a fleet-wide entitlement sweep against the RevenueCat API.

Identical to the defect `_shared/service-role.ts` was written to kill on 2026-08-14; five of six functions were migrated then and this one was missed.

**Why `gatewayVerifiesJwt: true` and not `false`.** The original author's reason for reading the claim rather than comparing keys was legitimate and is documented in the helper: this project has more than one valid service-role key in circulation — the GH Actions secret and the runtime-injected key are both correctly signed but not byte-identical — so strict equality 401s this nightly cron. `false` (exact match only) would have broken the caller, which is precisely the breakage that caused authentication to be deleted elsewhere in this codebase. The helper is two-mode for exactly this: it accepts the injected key **or** an authentic `service_role` claim, keeping rotation tolerance without trusting an unverified token.

That mode is sound **only** because this change also adds `[functions.pro-entitlement-reconcile] verify_jwt = true`. **Code and config must ship together, and this function must never be deployed with `--no-verify-jwt`** — a note to that effect sits in `config.toml` beside the pin.

**The registry is now exactly complete: 75 functions, 75 entries, no gaps and no orphans.** That matters beyond this one fix — `_shared/service-role.ts` states that its `gatewayVerifiesJwt` flag "is checkable against that file in review". Until now that was not true for one function, and that function was the one still trusting an unverified claim.

### A verification lesson worth keeping

Two functions in earlier batches (`gear-cpsc-recall-sync`, and this one) ended up **calling the shared gate without importing it** — a scripted edit silently failed. Both still passed the TypeScript **parse** check, because parsing does not resolve identifiers. In production each would have thrown `isServiceRoleRequest is not defined` on every invocation, taking down two crons.

Parse-clean is not correct-clean. There is now a symbol-resolution check — for every function, if it *calls* a shared gate it must *import* it from the right module (and no dead imports) — run across all call sites: **56 verified**. Until edge functions get a real type-check in CI, that check should be re-run after any bulk edit.

## Remediation log, batch 7 (2026-09-07) — per-user quotas

Closes the batch-5 scope boundary. Gating answered *who is calling*; nothing answered *how much they may have*, so every user-scoped model endpoint was an unmetered per-account endpoint billed to Villie. **23 functions** now carry a per-user hourly budget.

**`135_ai_rate_limits.sql`** — an `ai_rate_limits` counter table plus `consume_ai_quota(user_id, fn, limit, window_seconds)`.

- **The decision lives in SQL because it must be atomic.** A read-then-write in the edge function is a TOCTOU race: N concurrent requests all read the same count and all pass. The RPC decides and increments in ONE `INSERT … ON CONFLICT DO UPDATE … WHERE count < limit RETURNING` — Postgres locks the row, so concurrent callers serialise and the overflow gets zero rows back.
- **Fixed window, not sliding.** Sliding needs every timestamp retained and an aggregate per check; fixed needs one row and one upsert. The cost is the standard boundary burst, which is a fine trade for a cost control.
- **Deny-all table shape** (RLS on, no policies) — the pattern already used by `events_partner_feeds` / `specialist_invites` / `push_sends`. `EXECUTE` is granted to `service_role` only: a client that could call this could reset its own quota.
- `p_user_id` is passed in rather than read from `auth.uid()` because the invoker is `service_role`. That is safe **only** because the id was already established from a verified JWT via `getCallerUserId`.

**Verified by execution** against Postgres 16 (not asserted):

| Property | Result |
|---|---|
| Sequential limit | limit 2 → `t/1`, `t/0`, `f/0` + retry_after |
| **Atomicity** | **40 concurrent callers, limit 10 → exactly 10 allowed, 30 denied, stored counter = 10** |
| Per-function isolation | separate budget per `fn` key |
| Window rollover | 1s window: exhausted, then allowed again after expiry |
| Self-cleanup | stale buckets pruned, 1 row retained |
| Deny-all | `authenticated` gets `permission denied` on both table and function |

### Placement rules (the part that is easy to get wrong)

- **Default: immediately after auth, before any model call.** Uniform placement means it covers every downstream branch; deferring it deeper per-function risks a path that skips it. The side effect is that malformed requests also consume budget — correct for abuse control, and harmless for a well-behaved client.
- **Exception — `milk-trust-narrative`: below the 24h cache lookup.** This is called on *every* `DonorProfileScreen` view and the overwhelming majority are cache hits costing nothing. Charging them would have rate-limited a mother for simply browsing donors — a 20/hr ceiling reached after 20 profile views while Villie spent nothing. The budget must bound the expensive operation, not the cheap one.
- **Service-role paths are never charged.** `ai-daily-checkin` and `home-feed-curator` both have cron callers that legitimately run across many users; only the user path consumes quota.
- **`room-ai-companion` is deliberately excluded** — it already enforces 3/user/room/hour off `ai_companion_mentions`. It was the model for this design, not a target of it.

### Fail-open, deliberately — and the asymmetry with the auth gates

`consumeQuota` returns `allowed: true` and logs loudly if the ledger itself errors (DB unreachable, migration not yet applied). This is a **cost** control, not a safety control: the alternative is that a transient database problem silently blocks a postpartum mother from her check-in reply. An attacker cannot usefully induce that state — they would have to break the database, at which point the quota is not what is protecting you.

Note the contrast with `service-role.ts`, which fails **closed**. Different question, different default: "may this caller act at all" must fail closed; "have they had too much" may fail open.

### Client-side

A 429 would otherwise have surfaced the raw wire string `rate_limited` in an `Alert` — meaningless to a user and alarming at 3am. `api/ai.ts`'s shared `callEdgeFunction` now maps 429 to a translated message using `Retry-After`, so it says *when* rather than just *no*. EN/ES keys added under `errors.rateLimited`; parity re-verified (2,134 each, nothing removed).

**Limits** live in one table in `_shared/rate-limit.ts`. Sizing principle: comfortably above the busiest real session, low enough to stop a script. Vision endpoints are tightest (20/hr); `milk-questionnaire-coach` is deliberately generous (80/hr) because the donor questionnaire coaches each of ~12 answers and she may revise. A function with no entry logs a warning rather than silently running uncapped.

**Verification:** all 100 edge files parse clean; `tsc --noEmit` clean; the symbol-resolution check passes at **101 call sites** with no missing or dead imports; and a coverage audit confirms 23 limits ↔ 23 wired functions with matching keys and no orphans in either direction.

## Remediation log, batch 8 (2026-09-07) — room-message integrity (Connect pre-launch gate)

`136_security_room_message_integrity.sql`. Connect is hidden in `AppNavigator`, so no app user is exposed today — but RLS has been enforcing since migration 040 and `room_messages` is reachable through PostgREST with any authenticated session, so the surface is live on hosted. **This was the gate blocking Connect from ever being un-hidden.**

Three vectors, not the two originally reported:

1. **INSERT never constrained `message_type`.** `messages_insert_members` (`007:52-61`) checked sender and membership only, while the column accepts `system | ai_companion | expert`. `scan_room_message_async()` (`027:115-120`) treats those three as trusted and marks them `clear` **inline, without ever calling the classifier**. So a member could post as an `expert` and skip the Haiku crisis + moderation scan entirely — in a maternal-mental-health chat whose safety model is that every user message is screened for self-harm before anyone sees it. The same message renders under the gold "✨ Villie · AI companion" badge or as an official system card, so it is also clinical-authority impersonation to an audience of postpartum mothers.

2. **INSERT never constrained `ai_scan_status`** — found while reading the trigger, *not* in the original finding. The trigger's first statement is `IF NEW.ai_scan_status <> 'pending' THEN RETURN NEW` (`027:111-113`), an idempotency guard. Since the policy never pinned the column, a member could insert an ordinary `user` message with `ai_scan_status = 'clear'` and the trigger returned immediately. No scan, instantly visible (the read policy admits `clear`), **and no impersonation required**. This was the simplest bypass of the three and would have survived a fix that only addressed `message_type`.

3. **UPDATE was row-scoped, never column-scoped.** `messages_update_own` (`007:63-66`) pinned `sender_user_id` in USING and WITH CHECK — which *row*, never which *column*. A sender could flip her own `ai_scan_status` to `clear` (releasing a message the classifier had held as `flagged` or routed as `crisis`), rewrite `body` after the scan cleared it (the trigger fires on INSERT only — scan-then-swap), or flip `message_type` post-insert to reach vector 1 by another door.

**Fix.** INSERT now additionally requires `message_type = 'user'` and `ai_scan_status = 'pending'`. The UPDATE policy is **dropped** rather than narrowed: no client code updates this table — `api/community.ts` touches `room_messages` exactly twice, an INSERT of `{room_id, sender_user_id, body}` at `:171-173` and a SELECT of `ai_scan_status` at `:246-247`. There is no edit- or delete-message feature, so nothing is granted that isn't used. With RLS on and no UPDATE policy, every member update is denied.

**Verified by execution** — the vulnerability was *reproduced first* against the original 007 policies, then the migration applied and the identical attacks re-run:

| Attack (as a room member) | Before | After |
|---|---|---|
| insert `message_type='expert'` | **succeeded** | RLS violation |
| insert `message_type='ai_companion'` | **succeeded** | RLS violation |
| insert `ai_scan_status='clear'` | **succeeded** | RLS violation |
| self-clear own pending message | **cleared 3 rows** | 0 rows affected |
| normal user message | ok | ok (`user` / `pending`) |

And the legitimate trusted-message producers are untouched — as `service_role`: the `ai_companion` pre-cleared insert, the `system` weekly digest, and `room-message-scan`'s verdict PATCH all still succeed.

*Harness note:* the first run showed every insert failing even **before** the fix, which would have been a false pass. Two stub defects caused it — no `USAGE` on the `auth` schema (so `auth.uid()` raised inside the policy and surfaced as a violation), and no SELECT policy (so `INSERT … RETURNING` was refused). Worth recording: a security test that fails closed for the wrong reason looks exactly like a security test that passes.

### If an edit/delete-message feature is ever built

Add a **new** policy scoped to only the columns it needs (`is_deleted` / `deleted_at`). Do not restore `messages_update_own` — and note that permitting `body` edits reintroduces scan-then-swap unless the classifier is re-run on UPDATE.
