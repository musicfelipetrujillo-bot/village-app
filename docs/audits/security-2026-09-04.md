| # | Finding | Severity | Fix |
|---|---|---|---|
| R-1 | Any user could self-grant `is_pro` / `is_clinical_reviewer` / `is_event_reviewer` via `PATCH /users?id=eq.<self>` | **Critical** | `133_security_users_column_scope_update.sql` — table-wide UPDATE replaced with an 11-column allowlist |

### R-1 — self-granted privileges (critical)

`users_update_own` (`002_v1_rls_policies.sql:18`) scoped which *row* a caller may update but never which *columns*, and Supabase's default table-wide `GRANT UPDATE` made every column writable by its owner. The three privilege flags live on that same self-writable row (`043:20`, `046:35`, `110:20`).

Reachable consequences: publish arbitrary unreviewed AI health content to every user via `approve_content_row` (042:299); control the public events feed; free villie Pro.

**This also explains why migration 110's Pro gate looked airtight but wasn't.** The SQL enforcement in 110 is correct — playback ids nulled, RLS hides locked rows. The *flag it reads* was self-writable, so the gate was bypassed one level up. R-1 is what makes 110 actually hold.

Follows the `095` pattern, including its hard-won lesson: a column-level `REVOKE` is a **no-op** while a table-wide grant exists.

Verified by execution against Postgres 16 (stub schema, real grants): escalation `UPDATE` → `permission denied`; email takeover → `permission denied`; ordinary profile edit → succeeds; SELECT unaffected, so clients still read `is_pro`.

### R-2 — SMS and push open relays (critical)

Both functions carried an "Auth: service role only" header comment and performed **no authorization at all**. `verify_jwt = true` is not a substitute: it proves only that the bearer is signed by this project's JWT secret, and **the anon publishable key is exactly such a token** — it ships in the mobile bundle and on the marketing site.

This is the load-bearing insight of the whole review: it means every "server-only" function without an in-code gate is effectively internet-public *regardless of gateway settings*. Reachable: arbitrary SMS from Villie's Twilio number (toll fraud + smishing from a trusted number); arbitrary push to any user list, with caller-supplied `bypass_prefs: true` overriding notification preferences **and** quiet hours.

All 9 existing callers were verified to send `SUPABASE_SERVICE_ROLE_KEY` before gating, so no caller breaks.

### R-3 — specialist approval no-op (high)

`013_v1_admin_approval.sql:49` dropped `"Specialists are publicly readable"`; the policy actually created in `002:22` was named `specialists_select_all`. `IF EXISTS` swallowed the miss and the permissive `USING (true)` survived ~120 migrations. `015_v1_rls_audit.sql:3` asserts the control was in place, which is why it went unnoticed.

Exposed to **anon**: `phone`, `address_line1`, `stripe_account_id`, and `admin_rejection_reason` for pending and rejected practitioners.

Verified before dropping: the website never reads the table; 7 of 8 edge functions use service-role; the 8th (`create-payment-intent`) runs under the caller's JWT and retains `authenticated` read of approved rows.

### R-5 — fabricated clinical attribution (high)

`ManualScrollV3.tsx` substituted a placeholder titled "What to expect this week", attributed to **"Dr. Priya Nair, MD · pediatrician · villie"** — a person who does not exist — playing a public Mux sample clip.

Not an edge case: `get_manual_week_intro` filters `locale` exactly with no `en` fallback (`110:184-187`), so for a Spanish-speaking user under the English-first Pro launch **no week ever resolves** — she got the fake pediatrician on all 52 weeks, as did paying Pro subscribers in place of purchased content. `docs/PRO_VIDEO_LAUNCH_RUNBOOK.md`, added in the same commit as the locale-scope migration, documents the intended behaviour as "she gets no week-intro slot at all (it hides…)". Code contradicted its own runbook.

The `.catch` now also fails closed: it previously substituted a playable object carrying no `is_locked`, so `openWeekIntro` skipped the paywall — a transient network error handed free-tier users a playable card.

## Closed: `095` deferred item — donor `lat`/`lng` (no action)

`095_security_milk_donor_pii_column_revoke.sql:37-40` deferred revoking `milk_donor_profiles.lat/lng` pending verification. **Closing it: no change needed.**

- Coordinates are **ZIP-centroid derived**, not house-level geocodes (confirmed by the product owner, 2026-09-04). A ZIP centroid is coarser than the `zip_code` and `city` columns already selectable on the same row, so revoking buys no privacy.
- Independently, nothing in the repo writes these columns — no mobile code, no SQL, no edge function, no seed. They are populated out-of-band.
- A blanket revoke would be actively harmful: column grants are role-wide, not row-aware, so it would break a donor reading **her own** profile (`getMyDonorProfile`) and `listSavedDonors`. `DonorMapScreen` is unaffected either way — it reads through the `search_donors_near` SECURITY DEFINER RPC, which ignores column grants.

**Revisit only if** donor coordinates ever become precise geocodes. At that point the fix is a separate coarsened column plus jitter in `search_donors_near` — not a grant change.

## Remediation log, batch 2 (2026-09-05) — the gateless-function class

Re-derived the gateless set against this branch rather than trusting the review's list (which came from the stale checkout). Detecting *any* authorization signal — shared gate, `auth.getUser`, key compare, signature verification, 401 path — leaves **13 functions with no authorization of any kind**. Eleven are now gated; two are correctly public and stay that way.

**Service-role gate (8).** Every caller verified to send `SUPABASE_SERVICE_ROLE_KEY` before gating — `pg_cron` via `current_setting('app.service_role_key')` (`014_v1_cron_jobs.sql:18`), GH Actions via the repo secret (`supabase-crons.yml:168`). None break.

| Function | Was reachable as | Caller |
|---|---|---|
| `appointment-reminder` | drive the SMS+push sweep, write `twilio_reminder_sent` | pg_cron /15m |
| `events-geocode` | burn the Google Geocoding quota, write event coords | pg_cron |
| `events-ingest-ics` | trigger partner-feed ingest; fetches remote ICS, writes events | pg_cron |
| `refresh-stale-summaries` | one Anthropic call per stale specialist — an open tap on the bill | pg_cron daily |
| `week-nudge-notify` | push fan-out with attacker-tuned windows; `push_sends` pollution | GH Actions hourly |
| `trending-publish-notify` | Buzz publish push fan-out to the user base | pg_cron |
| `npi-verify` | **flip `specialists.npi_verified = true`** — forge the credential badge | **none in-repo** |
| `home-feed-curator` (batch) | fleet-wide Haiku fan-out on demand | pg_cron + mobile |

`refresh-stale-summaries` did not even accept the `Request` (`Deno.serve(async () => {`), so there was nothing to authorize against. `npi-verify` has no caller anywhere — deployed, unreferenced, and writing a trust signal.

**`home-feed-curator` — two-sided, because it has two legitimate callers.** `batch` is now service-role only. `single` accepts service-role for any `user_id`, otherwise requires a valid user JWT and forces the target to that caller's own id. This closes a live **IDOR**: `user_id` came straight off the body and was never checked, so any request could regenerate and overwrite another user's `home_feed_cache`. A body `user_id` naming someone else is refused (403) rather than silently retargeted, so a buggy client fails loudly.

**User-JWT gate (3)** — new `_shared/user-auth.ts`. `geocode-zip`, `daycares-nearby`, `gear-upc-lookup` are mobile-only and each calls a **billable third-party API** (Google Geocoding, Google Places, Go-UPC/UPCitemdb). They were open to anyone holding the anon key. They act on no specific user's records, so "a valid user is asking" is the right bar; the helper's docstring is explicit that anything touching a specific user's data must use `getCallerUserId` and compare ids instead.

**Deliberately left public (2):** `manual-og` (`verify_jwt = false`, no writes — renders OG meta for share links; gating breaks every link preview) and `specialist-invite-accept` (`verify_jwt = false` — the invitee is anon pre-signup; it is invite-token-gated by design). `specialist-invite-accept` still needs the **non-atomic invite claim** fixed — see Open #2.

`_shared/user-auth.ts` is the counterpart to `_shared/service-role.ts`, and directly addresses the audit's duplication finding: the JWT-resolution block was about to become its fourth copy.

**Verification:** all 12 changed/added function files parse clean (TypeScript parser). `deno check` could not run — Deno cannot resolve npm specifiers inside this pnpm workspace, and attempting it rewrites `package.json` (reverted). **Standing gap: edge functions still have no type-check in CI**, which is why a parse-only check is the best available signal here.

## Remediation log, batch 3 (2026-09-05) — the IDOR class

Batch 2 closed "no gate at all". This closes the subtler class: functions that checked *a* caller but not *which* caller, then read or wrote with the service-role client — so RLS never applied.

| Function | Unchecked input | Was reachable as | Rule now |
|---|---|---|---|
| `ai-daily-checkin` | `checkin_id` | AI reply derived from **another mother's free-text mental-health entry**, plus a PATCH of `ai_reply`/`crisis_flagged` onto her row | caller must own the check-in |
| `ai-match` | `user_id` | victim's `pregnancy_stage` + `insurance_provider` into an LLM, readable back out of the returned reasons | target forced to caller |
| `room-auto-match` | `user_id` | victim's stage/due-date/city into a "reason"; overwrote her `room_match_suggestions` | target forced to caller |
| `room-icebreaker` | `user_id` | overwrote any user's icebreaker for any room | target forced to caller |
| `room-ai-companion` | `message_id` | post an AI reply into a room you aren't in, under the trusted gold badge; **and exhaust another user's rate limit**, which is keyed to the sender | caller must be the message's sender |
| `ai-event-relevance`, `ai-perk-recommender`, `ai-gear-tip` | `user_id` | inference leak about another mother + a free Haiku endpoint | service-role only (sole caller is `home-feed-curator`) |
| `milk-donor-qa` | `donor_profile_id` | **owner-only health data** recited by an LLM | owner-scoped + visibility |
| `milk-trust-narrative` | `recipient_preferences` | poison a **globally-cached** donor trust narrative | input removed |

**Not-yours is answered with the same 404 as not-found** in `ai-daily-checkin`, `room-ai-companion`, `milk-donor-qa` and `milk-trust-narrative`. A distinct 403 would confirm that a given id exists — an enumeration oracle over mental-health records, private-room messages, and donor profiles.

**`milk-donor-qa` was a straight RLS bypass, not a design choice.** `milk_questionnaire_responses` is owner-only under RLS (`005_v2_milk_rls.sql:39-43`) — medications, conditions, alcohol, smoking. The function read it with the service-role client and injected it wholesale into the prompt, while the system prompt forbade revealing only "address or contact info". Any signed-in user could iterate donor ids and ask for the disclosures verbatim; the model answers from the data it was given, so no jailbreak was needed. The questionnaire is now fetched **only** when the caller is the donor herself — not fetched and discarded, since unused PHI in memory is still PHI. Everything else in the prompt (profile, badge level, diet flags) is authenticated-readable by design, so recipient-facing Q&A still works on the data it is permitted to use.

**`milk-trust-narrative` folded a per-viewer input into a shared artifact.** `recipient_preferences` was free text steering a narrative written to `milk_trust_badges.ai_trust_narrative` and served to every user for 24h — re-poisonable on expiry. The only caller (`DonorProfileScreen.tsx:118`) never passed it, so it was reachable only by hand-crafted request; deleting it costs nothing. The client parameter was removed too, rather than ignored server-side, so it can't look like a working feature.

**New shared helper:** `resolveTargetUser(req, bodyUserId, isService)` in `_shared/user-auth.ts` — service role may target anyone, a signed-in user only herself, and a body `user_id` naming someone else is **refused (403), not silently rewritten**. Quietly retargeting would hide a client bug behind an apparent success.

**Verification:** all 11 changed function files parse clean; `tsc --noEmit` clean for the mobile signature change. Same caveat as batch 2 — no Deno type-check available in this workspace.

## Open — not fixed here, ranked

1. **`pro-entitlement-reconcile`** (medium) — the one function still decoding its JWT without signature verification, and absent from `config.toml`'s 75 pins. Found independently by two reviewers. Branch `sec/service-role-gate-pro-reconcile` appears to target this but has not landed.
2. **Remaining abuse surfaces** (medium) — distinct from the IDOR class, now that it is closed. `events-harvest` (**SSRF**: fetches an arbitrary `probe.url` server-side); `ai-translate` / `ai-triage` / `ai-profile-qa` / `ai-followup-questions` / `gear-vision-identify` / `agents-*` (free LLM/vision proxy — no per-user target to scope, so these need a user gate plus rate limiting, not an ownership check); `ai-review-summary` (any caller regenerates a specialist's cached, all-users-visible summary, on demand activating prompt-injection payloads planted in reviews). `specialist-invite-accept`'s **non-atomic invite claim** also remains: concurrent requests on one token can both mint pre-approved, patient-accepting specialist accounts.
4. **Room chat impersonation + scan bypass** (high) — unconstrained `message_type` lets a member post as `expert`/`ai_companion` and skip the crisis scan; `messages_update_own` permits self-clearing `ai_scan_status`. Connect is hidden in-app but live on hosted. **Must be fixed before the Connect tab is un-hidden.**
5. **`service_role` key in `apps/mobile/.env`** (high) — not bundled and correctly gitignored, but wrong location. Move to Edge Function secrets and rotate.
6. **Keychain → AsyncStorage token downgrade** (medium-high) — falls back on first error and latches for the process; live in Release builds.
7. **Sign-out incomplete** (medium) — no `OneSignal.logout()`; `useUserStore` / vault / tracker never reset; `Sentry.setContext('user_meta')` not cleared.
8. **`vercel.json` has no security headers** (high, website) — no CSP/HSTS/X-Frame-Options on a domain serving a password-entry onboarding page.
9. **`index-genz.html` still deployed** (high, website) — reachable, `action="…/REPLACE_ME"`, shows a success screen and sends nothing.
10. **Dependencies** — 2 critical / 29 high, but only two reach users' devices: `ws` (via `@supabase/supabase-js`) and `nanoid` (via `@react-navigation/native`). The rest are build-time.
